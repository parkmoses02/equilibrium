# DD→UU 스윙업: 카트가 궤적에서 벗어나던 문제와 해결 (2026-11-24)

## 결론

DD→UU 스윙업이 잘 되기 시작한 것은 2026-11-24 20:50경(KST)에 적용한 두 가지 변경 덕분이다.

1. **UU 궤적(`uu_frames.h`)을 시스템 식별로 피팅한 모델로 다시 설계했다.** 관성과 관절 마찰(b1, b2, fc1, fc2)을 모두 반영했다.
2. **UU 스윙 중에도 카트 위치 피드백을 넣었다.** 출발점 기준 궤적 위치 오차 `x − (swingOrigin + r.x)`에 프레임 위치 게인의 50%를 적용하고, ±1 m/s²로 제한했다.

같은 날 앞서 넣은 칼만필터(EKF)와 시스템 식별(`double_sysid`, `fit.py`)은 이 두 변경의 전제 조건이었다. 다만 이것만으로 해결된 것은 아니다. 시뮬레이션에서 EKF를 쓰든 실제 상태값을 쓰든, 마찰이 있으면 기존 궤적은 실패했다.

## 증상

- `rq`(DD→UU)를 보내면 스윙 도중 XACTUAL(램프 위치)이 궤적표의 x에서 계속 벌어졌다. 결국 ±300 mm 한계에 닿아 `RAMP_POSITION_LIMIT`로 정지했다.
- DD→DU(`re`), DD→UD(`rw`)는 같은 시기에 잘 됐다. UU만 실패했다.

수정 전후 로그를 비교한 결과다. 편차는 스윙 시작점 기준 램프 x와 그때 쓰던 궤적표 x의 차이 중 최댓값이다.

| 로그 (KST) | 궤적 | rq 횟수 | 표 대비 최대 x 편차 | 결과 |
|---|---|---|---|---|
| 20:21 `device-monitor-261124-202139.log` | 기존 (마찰 없는 모델) | 1 | 약 300 mm (367스텝) | `RAMP_POSITION_LIMIT` |
| 20:51 `device-monitor-261124-205124.log` | 새 궤적 + 위치 피드백 | 5 | 32~119 mm (4회는 52 mm 이하) | 5회 모두 `CATCH UU` |

## 원인

20:21 실패 로그를 분석한 결과다.

1. 140스텝(0.7초)까지는 각도 오차 1~2° 이내로 궤적을 잘 따라갔다.
2. 150~180스텝에서 base가 맨 아래를 빠르게 지날 때, 실제 링크가 기준보다 0.5~1.5 rad/s 빨랐다. base 오차가 +11°까지 커졌다.
3. TVLQR 피드백이 이 각도 오차를 잡느라 카트를 기준보다 +0.3 m/s 빠르게 보냈다.
4. 스윙 중에는 카트 위치를 되돌리는 항이 없었다(`e[0] = 0`). 그래서 위치 오차가 쌓여 367스텝에서 300 mm 한계에 닿았다.

근본 원인은 궤적이 **관절 마찰이 없는 모델**로 설계됐다는 것이다. 마찰이 있는 실제 진자는 궤적과 다르게 움직였다. 그 차이를 피드백이 카트를 밀어서 메우면서 위치가 표에서 벗어났다.

`sim-uu-swing.cpp`는 펌웨어 루프 순서, 피팅 모델과 마찰, EKF, 엔코더 양자화, 램프를 모두 재현한다. 이 시뮬레이션도 362스텝에서 같은 이유로 멈췄다(하드웨어는 367스텝). 기존 궤적으로 조건을 바꿔 가며 10회씩 돌린 결과는 아래와 같다.

| 조건 | 포착 |
|---|---|
| 마찰 없음, 실제 상태값 | 10/10 |
| 마찰 없음, EKF | 10/10 |
| 마찰 있음, 실제 상태값 | 4/10 |
| 마찰 있음, EKF (하드웨어와 같은 조건) | 0/10 |

마찰이 결정적이었다. 상태를 완벽히 알아도 마찰만 넣으면 실패했다. 마찰이 없어 성공한 경우에도 카트가 기준에서 최대 160 mm 벗어났다. 기존 궤적 자체가 x = 173 mm까지 가므로 300 mm 한계까지 여유가 거의 없었다.

## 시도했지만 효과가 없었던 것

모두 기존 궤적에 시뮬레이션으로 시험했다. 결과는 0~1/10이었다.

- EKF 과정잡음(accelStd)을 30에서 2로 낮추기. 프레임마다 튀던 피드백 가속도는 5.3에서 0.8 m/s²로 줄었지만 마찰이 있으면 여전히 0/10이었다. EKF 각속도 잡음은 원인이 아니었다.
- 각속도 게인 절반, 전체 게인 절반
- 가속 제한 8 m/s²
- 위치 피드백만 추가하기 (DD→UD 방식)

게인이나 추정기를 조정하는 것으로는 안 됐고, 궤적을 실제 모델에 맞춰야 했다.

## 해결 과정

1. **시스템 식별** (`double_sysid` 펌웨어 + `simulation/sysid/fit.py`)
   - 자유 감쇠 f1~f4와 처프 c2를 실행했다. 처음 시도한 `c`(c3)는 `ANGLE_LIMIT`로 멈췄다.
   - `fit.py --refine --write`로 `model_params.h`를 만들었다. 관성, 결합항, 점성·쿨롱 마찰, 입력 지연이 들어 있다.
2. **궤적 재설계** (`simulation/dd-uu/design.py --fitted`, CasADi 설치)
   - 피팅 모델로 카트 한계 ±0.24, ±0.18, ±0.14 m의 궤적 세 개를 설계했다.
   - 설계 중 버그를 하나 고쳤다. 쿨롱 마찰을 그대로 선형화하면 궤적 끝 게인이 1000을 넘어 EKF와 함께 발산했다. 그래서 궤적 rollout에는 전체 마찰 모델을 쓰고, 게인 계산(Jacobian)에서만 쿨롱 항을 빼고 점성 마찰만 쓴다.
   - 새 궤적의 카트 최대 이동은 +177 mm다.
3. **UU 스윙 위치 피드백** (`upright.h`)
   - DD→UD와 같은 위치 피드백을 UU 스윙에도 넣었다.
   - 이를 위해 UU 출발 때도 `swingOrigin`을 저장한다.
4. **시뮬레이션 검증** (`sim-uu-swing.cpp`, 조건별 10회)

   | 조건 | 기존 궤적 | 새 궤적 + 위치 피드백 |
   |---|---|---|
   | 모델 정확 | 0/10 | 10/10 (각도 오차 약 1°) |
   | J1, J2, d1 각각 ±2% | — | 10/10 |
   | 쿨롱 마찰 0.7~1.3배 | — | 10/10 |
   | 점성 마찰 0~3배 | — | 10/10 |
   | 관성 전체 ±5% | 0/10 | 0/10 |

5. **하드웨어**: 20:51 로그에서 `rq` 5회가 모두 포착됐다. 20:56에 "dd→uu 스윙업이 이제 매우 순조롭게 잘된다"고 확인했다.

## 피팅 모델의 마찰은 어떻게 구했나

마찰은 시스템 식별 실험 데이터에 모델을 피팅해서 구했다. 실험은 11/24 19:54 로그 `logs/device-monitor-261124-195458.log`에 모두 들어 있다. `model_params.h`의 머리말에 적힌 입력 로그 4개 중 SYSID 데이터가 있는 것은 이 파일뿐이다.

### 실험 (`double_sysid` 펌웨어)

| 실험 | 횟수 | 조건 | 주로 정해지는 값 |
|---|---|---|---|
| 자유 감쇠 f1 | 1 | base +60°, tip 일직선 | 느린 모드, 큰 진폭: J1, d1, b1 |
| 자유 감쇠 f2 | 1 | base +15°, tip 일직선 | 작은 진폭: 점성 마찰과 쿨롱 마찰 구분 |
| 자유 감쇠 f3 | 1 | base +30°, tip 절대각 -30° | 빠른 모드: J2, C |
| 자유 감쇠 f4 | 1 | base 매달린 채, tip만 +45° | 팔꿈치: J2, b2, fc2 |
| 처프 c (amp 1.2) | 1 | 카트 0.3→5 Hz | `ANGLE_LIMIT`로 중단 |
| 처프 c2 (amp 0.8) | 2 | 카트 0.3→5 Hz | 관성·결합항, 입력 지연 |

f1~f4의 조건은 `simulation/sysid/README.md`의 권장 자세다. 각도 측정 도구가 없어 실제 시작 각도는 눈대중으로 맞췄다. 자유 감쇠는 모터를 끄고 카트를 고정한 채, 링크를 손으로 잡았다가 놓아서 기록했다. 흔들림이 줄어드는 모양이 마찰을 정하는 핵심 근거다.

### 마찰 모델 (`simulation/sysid/fit.py`)

- 점성 마찰: 피벗 b1·ω1, 팔꿈치 b2·(ω2 − ω1)
- 쿨롱 마찰: fc·sgn(ω) 대신 fc·tanh(ω / 0.05)를 써서 0 근처를 부드럽게 만들었다.

### 피팅 방법

1. 0.1초 구간마다 "일반화 운동량 변화 = 일반화 힘의 적분" 식을 세운다. 이 식은 관성·마찰 값에 대해 선형이라 경계 조건이 있는 최소제곱(`lsq_linear`)으로 푼다. 각가속도를 쓰지 않는 이유는 양자화된 각도를 두 번 미분하면 관성이 4~17% 낮게 편향되기 때문이다(합성 데이터 자체 검증 결과).
2. 운동이 모든 값을 같은 배율로 키워도 같아서 d2는 공칭값으로 고정한다.
3. 처프에서는 입력 지연을 0~30 ms 범위에서 1 ms 단위로 찾는다.
4. `--refine`: 1단계 결과에서 시작해서 0.6초 개루프 시뮬레이션 각도와 실측 각도의 차이가 최소가 되도록 다시 맞춘다.
5. `--write`로 `src/double_pendulum/model_params.h`에 저장한다.

### 결과

| 값 | 의미 | 결과 |
|---|---|---|
| b1 | 피벗 점성 | 9.35×10⁻⁶ N·m·s |
| b2 | 팔꿈치 점성 | 2.81×10⁻⁵ N·m·s |
| fc1 | 피벗 쿨롱 | 4.59×10⁻⁴ N·m |
| fc2 | 팔꿈치 쿨롱 | 1.12×10⁻⁴ N·m |

### 궤적 설계에서 마찰을 쓰는 방식

궤적 rollout에는 위의 전체 마찰 모델을 쓴다. 프레임별 게인을 계산하는 선형화(Jacobian)에서는 쿨롱 항을 빼고 점성 마찰만 쓴다. 쿨롱 항을 그대로 선형화하면 궤적 끝 게인이 1000을 넘어 EKF와 함께 발산했기 때문이다.

### 한계

- 쿨롱 마찰은 주로 자유 감쇠에서 나온 값이라, 거의 멈춘 상태에서는 실제와 다를 수 있다.
- 처프의 카트 가속도는 실측값이 아니라 램프 속도로 계산한 값이다.
- 자유 감쇠 피팅은 카트가 정지해 있다고 가정한다. 실험 중 카트가 밀렸다면 값이 틀어진다.

그래도 새 궤적은 시뮬레이션에서 쿨롱 마찰 0.7~1.3배, 점성 마찰 0~3배 범위에서 모두 10/10이었다. 마찰 값이 이 정도 틀려도 버틴다.

## 엔코더 오류 복구: "3차 다항식이 부족하다"

같은 날 EKF와 함께 만든 엔코더 오류 복구 코드에서 나온 이야기다. 코드는 `src/double_pendulum/state_estimator.h`의 "Encoder slip recovery" 부분이다. 스윙업 위치 오차 문제와는 별개다.

### 문제

HEDS 엔코더에서 인터럽트 사이에 A/B 두 신호가 한꺼번에 바뀌면, 방향을 알 수 없어 정확히 ±2카운트가 사라진다. 이전에는 이런 오류가 50 ms 안에 다시 나면 `REPEATED_ENCODER_EDGES`로 정지했다.

### 복구 방식

1. 오류가 난 순간부터 그 채널은 EKF 예측값만으로 구동한다.
2. 오류 뒤 깨끗한 프레임이 4개(20 ms) 모이면, 오류 앞 4프레임과 그 뒤 원시값에 "시간에 대한 3차 다항식 + 오류 프레임마다 계단 하나"를 최소제곱으로 맞춘다. 엔코더 값만 쓰기 때문에 모델 오차가 판정을 흔들지 않는다.
3. 오류 n개가 숨긴 카운트는 2m(m ∈ {−n, −n+2, …, n})뿐이라, 후보끼리 4카운트씩 떨어져 있다. 피팅한 계단 높이를 가장 가까운 후보로 반올림하고 엔코더 원점을 고친다.
4. 계단이 후보에서 1.5카운트 넘게 벗어나면 `unresolved`로 표시한다. 구동은 계속하고, 정지 후 `z`를 다시 하라고 안내한다.

### 3차 다항식이 부족했던 부분

링크가 빠르게 휘두를 때는 40 ms 동안의 각도 곡률을 3차 다항식이 따라가지 못해 사라진 카운트를 잘못 판정했다. 이 속도에서는 축이 인터럽트보다 빨라서 엣지를 놓친 것이므로, 사라진 카운트는 회전 방향 쪽에만 있을 수 있다(글리치 쌍은 합이 0). 그래서 0.6 rad/s를 넘으면 후보를 회전 방향 쪽으로만 제한했다. 0.6 rad/s는 한 프레임에 2카운트로, EKF 각속도 잡음의 약 3배다.

### 최종 방식이 나오기까지

1. 처음에는 한 스텝 예측값만으로 판정했다. 빠를 때 판정이 틀렸다.
2. 홀짝 제한, 운동 방향 사전 정보, 여유 규칙을 차례로 시도했다.
3. 혁신(innovation) 수열 피팅과 드리프트 모델도 시도했지만 둘 다 더 나빴다.
4. 최종: 고정 지연 "3차 다항식 + 계단" 피팅, 0.6 rad/s 초과 시 회전 방향 제한.

### 검증과 정지 조건

`simulation/sysid/test-estimator.cpp`로 각 40회 시험했다.

| 조건 | 결과 |
|---|---|
| 채널당 초당 약 1회 오류 | 1235건 중 남은 카운트 오차 0건, `unresolved` 5건 |
| 초당 약 5회 오류 | 남은 오차 0건, 정지 1회 |
| 엔코더가 완전히 죽음 | `ENCODER_LOST`로 정상 정지 |

다음 중 하나면 그 채널을 잃은 것으로 보고 `ENCODER_LOST`로 정지한다. 기존 `REPEATED_ENCODER_EDGES`를 대신한다.

- 한 사건에서 오류 프레임이 3개 초과
- 예측만으로 구동한 프레임이 12개(60 ms) 초과
- 측정값이 예측과 0.05 rad 넘게 달라 연속 3프레임 넘게 거절됨

11/24 로그의 `ENC_RECOVERY` 기록에서 `lost=1`은 없었고, `unresolved`는 2건이었다.

## 이어서 생긴 문제: 포착 후 카트가 + 방향으로 흐름

스윙업은 됐지만, UU를 잡은 뒤 카트가 + 방향으로 흘러 +30 cm를 넘어 정지했다.

- **원인 1:** UU 홀드에 카트 위치 피드백이 없었다.
- **원인 2:** 각도 바이어스(base +0.39°, tip +0.17°)가 있었다. 로그에서 카트는 약 +0.065 m/s로 꾸준히 이동했고, 이는 계산값과 거의 같았다.
- **해결:** UU 홀드를 피팅 모델 기반 LQI로 바꿨다. Q = (12, 60, 60, 2, 2, 2), R = 0.3에 위치 적분을 더했고, 바이어스를 적분항이 흡수해 카트를 z 근처로 되돌린다(`K_q`, `KI_Q`).
